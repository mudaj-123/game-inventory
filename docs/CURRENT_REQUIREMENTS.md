# 实体游戏库存管理系统：当前权威需求

更新日期：2026-09-20

本文件是项目当前需求、架构边界和实施优先级的权威来源。未来任何开发者或自动化代理
进入仓库后，都必须先阅读本文件，再审计现有实现并制定增量修改方案。历史规格仍保留用于
追溯，但与本文件冲突时以本文件为准。

## 1. 工作方式与长期目标

这是一个已经开发过一段时间的实体游戏库存管理系统，不是需要重新搭建的新项目。

- 修改前必须审视目录结构、README、规格文档、依赖、应用入口、模型、Schema、数据库
  配置、Alembic、Docker、CI、环境变量、测试、前端/PWA、扫码、认证、CSV、事务、
  备份、部署文档和数据库初始化方式。
- 先运行现有测试并记录基线；如测试依赖 PostgreSQL，遵循仓库约定启动测试数据库。
- 在现有实现上增量修改，不为追求“更现代”而推翻可用实现。
- 优先保护已有生产数据、库存正确性和兼容性；数据库结构变化必须通过 Alembic。
- 每个行为变化都要增加或更新测试。不得宣称未实际运行的检查已经通过。
- 重要决策、运维方法和已知限制必须写回仓库，不能只存在于聊天记录中。
- 除非涉及大量数据删除、不可逆兼容性破坏、真实生产凭据或无法代替用户决定的重大产品
  选择，实施过程应自主连续完成，不要求用户逐项回复“继续”。

## 2. 业务范围

系统主要管理以下实体商品：

- PlayStation 5 光盘；
- PlayStation 4 光盘；
- Nintendo Switch 卡带；
- Nintendo Switch 2 卡带；
- 未来可扩展的其他实体商品。

主要用户不是专业技术人员。店员使用 Android、iPhone 或电脑浏览器/PWA，配合 Bluetooth
HID 或 USB-C OTG HID 扫码枪连续操作。扫码枪视为键盘输入设备：输入条码，以 Enter 或
Tab 结束，系统处理后输入框自动重新获得焦点，随即可扫描下一件商品。

## 3. 当前主要生产架构

主要生产环境是一台长期放在实体店内的 Windows 10 x64 台式电脑：

- Intel Core i3-4130（2 核 4 线程）；
- 12 GB DDR3 内存；
- 约 500/512 GB SATA SSD，存放 Windows、PostgreSQL、Python、应用和主数据库；
- 1 TB HDD，存放历史文件和 PostgreSQL 自动备份；
- 同时承担店铺办公电脑、库存应用服务器和数据库服务器。

正式架构为：

```text
Windows 10
├── 原生 PostgreSQL（默认仅接受 localhost 连接）
├── 原生 Python 3.12 / FastAPI
└── 浏览器与店铺 LAN
    ├── 店铺电脑
    ├── Android
    ├── iPhone
    └── HID 扫码设备
```

约束如下：

- 正式店铺部署不依赖 Docker Desktop。
- 手机仅是客户端，不保存正式库存数据库，也不直连 PostgreSQL。
- `DATABASE_URL`、监听 host、port、日志和备份位置均通过环境变量或配置文件管理；不得在
  源码写死账号、密码或端口。
- FastAPI 应能监听配置化 LAN 地址和端口，例如 `0.0.0.0:18081`。
- PostgreSQL 原则上只监听本机，不为手机、LAN 或公网开放 5432。
- FastAPI/Web 只向确有需要的局域网或 Tailscale 网络开放。
- 禁止把 FastAPI 或 PostgreSQL 端口直接映射到公网。

## 4. Docker、云部署与 CI 的定位

已有 Dockerfile、Docker Compose、Nginx、GitHub Actions、PostgreSQL CI 测试和镜像构建能力
不得无分析删除。它们继续用于：

- 可选云端部署；
- 开发和自动化测试；
- 灾备与迁移；
- 构建可追溯镜像。

文档必须清晰区分：

1. Windows 店铺本地部署（默认、主要生产方案）；
2. Docker/云服务器部署（备用或可选方案）。

## 5. 库存事务不可退化的规则

系统必须继续支持入库、销售出库、管理员调整和撤销，并满足以下不变量：

1. 库存绝不能变成负数；
2. 使用 `client_scan_id` 或等价机制实现幂等；
3. 网络重试和重复扫码不能重复扣减或增加库存；
4. 并发扫码不能造成错误库存；
5. 所有库存变化必须留下只追加流水；
6. 流水不能通过普通业务操作删除或篡改；
7. 撤销生成关联的 `REVERSAL` 反向事务，不删除原流水；
8. 商品名、平台、条码等必要信息在流水中保留历史快照；
9. 两个客户端同时销售最后一件商品时，最终只能一个成功，库存为零；
10. 数据模型现有语义应优先保留，任何变更都必须兼容历史数据并使用 Alembic。

`inventory_transactions` 应继续表达客户端请求 ID、商品、条码/名称/平台快照、事务类型、
前后库存、关联事务、用户、设备和创建时间。不得把正式生产数据库改成 SQLite，也不得用
`create_all()` 代替生产迁移。

## 6. 条码识别与扫码体验

核心识别流程必须离线可用，优先级为：

```text
正式业务数据库中的已确认商品
→ 已导入数据库的本地 CSV 条码目录
→ 未知条码人工补录
```

- 不得让 IGDB、UPC 查询或其他第三方在线服务成为运行依赖。
- 条码始终作为字符串处理，保留前导零。
- CSV 源文件使用 UTF-8，导入必须兼容 UTF-8 BOM。
- 未知条码允许录入商品名、平台和必要资料；确认后永久自动识别。
- CSV 可以初始为空，并允许用户后续维护和重新导入。

入库模式：扫码、自动识别、库存加一、展示商品与当前库存、声音/视觉提示、恢复焦点。

出库模式：扫码、校验库存、库存减一、展示剩余库存与重要预警、恢复焦点。

不得要求店员每扫一件都点击提交按钮；Enter 和 Tab 均应触发提交。

## 7. 认证与权限

- 继续保留 ADMIN / STAFF 权限边界。
- STAFF 可执行日常扫码并按既有规则查看和撤销自己的流水。
- ADMIN 可管理必要的运营数据、执行有原因记录的库存调整、查看全局流水与预警。
- 会话、密码、CSRF 和数据库凭据不得保存到浏览器持久化存储。
- 局域网 HTTP、Secure Cookie 和 PWA 安全上下文之间的关系必须明确解决和记录；不能提供一套
  实际无法登录或无法注册 Service Worker 的生产说明。

## 8. 库存预警

继续保留或完善以下状态：

- `LOW_STOCK`；
- `SOLD_OUT`；
- `OVERSTOCK`；
- `STALE_STOCK`。

预警在状态跨越时生成或关闭，不能因刷新页面反复创建相同记录。后台至少能够查看当前售罄、
低库存、积压和未识别/待完善商品。扫码触发重要状态时，手机端应立即给出清晰提示。若新增或
修改预警表，必须使用 Alembic 并尽量沿用已有设计。

## 9. Windows 自动启动和运维脚本

目标体验为：Windows 开机后 PostgreSQL 自动启动，随后 FastAPI 自动启动，系统可供店铺设备
访问，不要求用户每次手工运行 Python。

应在 `scripts/windows/` 提供与实际实现一致的 PowerShell 工具，例如：

- `setup.ps1`；
- `start.ps1`；
- `stop.ps1`；
- `restart.ps1`；
- `install-service.ps1`；
- `backup.ps1`；
- `restore.ps1`；
- `health-check.ps1`。

可选择 Windows Service、Task Scheduler、WinSW 或 NSSM，但应优先减少第三方依赖、固定工具
来源和版本，并说明安装、卸载、启动、停止、重启、状态与日志查看方法。启动逻辑必须能报告
PostgreSQL连接或迁移失败，不得静默失败。

## 10. 备份与恢复

备份使用 PostgreSQL 官方 `pg_dump`，不直接复制数据库 data directory。

- 自动生成 custom-format 备份；
- 文件名包含 UTC 时间；
- 输出目录可配置，生产建议指向 1 TB HDD；
- 保留天数可配置；
- 先写临时文件，成功后再原子改名；
- 失败返回非零状态并写清晰日志；
- 提供手动备份、恢复和健康检查脚本；
- PostgreSQL 工具路径、连接信息和目标目录不得硬编码；
- 密码不得出现在源码、命令输出或日志中。

“存在备份文件”不等于备份完成。必须在安全测试环境实际验证：

```text
pg_dump
→ 创建新的临时数据库
→ pg_restore
→ Alembic upgrade
→ 校验关键表、用户、商品、库存和流水
```

恢复演练不得覆盖或删除生产数据库。HDD 本地备份不能替代额外故障域中的加密副本。

## 11. 云数据库迁移到本地

不能假设生产数据可以重新开始，也不能通过 CSV 手工重建完整数据库。迁移流程必须是：

```text
冻结旧系统写入
→ 对旧 PostgreSQL 执行 pg_dump
→ 校验备份
→ 恢复到 Windows 本地 PostgreSQL
→ alembic upgrade head
→ 校验数据与约束
→ 切换客户端
```

必须保留商品、库存、全部流水、用户、权限、预警、条码映射和历史数据。迁移前后应比较关键表
行数，验证条码唯一、库存非负、撤销关联完整，并准备失败时回到旧系统的步骤。

## 12. 局域网、Windows 防火墙和远程访问

- 店铺网络应使用 Windows Private Network Profile。
- 建议在路由器配置 DHCP Reservation，保持服务器 LAN 地址稳定。
- Windows 防火墙只能开放必要 Web 应用/端口，并限制到 Private/LocalSubnet 或明确的
  Tailscale 范围；不得关闭整个防火墙。
- PostgreSQL 不向 LAN 或公网开放。
- 文档应说明 FastAPI 监听地址、访问 URL、Android/iPhone 测试和 PWA 限制。
- 将来店外访问优先使用 Tailscale 到 FastAPI/Web。
- 禁止路由器公网端口映射到 FastAPI，也禁止公网暴露 PostgreSQL 5432。

## 13. 性能、日志和故障恢复

目标硬件有限，系统应保持单体、简单和低维护：

- 不引入 Kubernetes、微服务、Elasticsearch或不必要的队列；
- Redis 只有在现有功能有明确不可替代需求时才能加入；
- 不让 Docker Desktop 成为生产依赖；
- 扫码响应和数据库事务正确性优先。

至少提供：

- 应用启动和退出日志；
- 应用错误日志；
- 数据库连接失败日志；
- 备份和恢复日志；
- 自动启动失败信息；
- 明确的日志路径、轮转与查看方法。

健康检查应验证 FastAPI 和数据库，而不是只返回固定的应用状态。数据库不可用时应返回不健康
状态且不得泄露连接字符串或密码。

## 14. 测试要求

每次相关修改后运行适用检查，最终测试矩阵至少覆盖：

1. 单元测试；
2. API 测试；
3. PostgreSQL 集成测试；
4. 并发销售最后一件商品；
5. 幂等和重复扫码；
6. 防负库存；
7. 撤销和重复撤销；
8. CSV 导入、UTF-8 BOM 和前导零；
9. ADMIN / STAFF 权限；
10. 预警状态跨越；
11. dump、临时库 restore 和数据校验；
12. Windows PowerShell 脚本静态检查及真实 Windows 验收；
13. Docker/CI 回归。

真实 Windows Service、Task Scheduler、防火墙、证书、手机 PWA 和原生 PostgreSQL 的行为最终
必须在 Windows 10 店铺机或等价测试机验收；无法在非 Windows CI 中验证的项目要明确记录，
不能伪称通过。

## 15. 实施顺序

建议按以下顺序持续推进，每阶段完成后运行相关测试并先修复失败：

1. 审计仓库并建立测试基线；
2. 更新长期规格和架构决策；
3. 整理原生运行配置、监听地址、Cookie/HTTPS 和日志；
4. 验证本地 PostgreSQL 与数据库健康检查；
5. 实现 Windows 安装、启动、停止、重启和自动启动；
6. 实现 Windows 备份、恢复和临时库恢复验证；
7. 固化云数据库迁移步骤；
8. 配置最小 LAN 防火墙边界和 Tailscale 文档；
9. 验证并完善扫码、库存事务、预警和管理员功能；
10. 补齐测试和端到端检查；
11. 更新 README、部署手册、故障恢复与已知限制。

## 16. 禁止事项

除非审计证明必要并有明确迁移方案，否则不得：

- 重写整个项目或更换 FastAPI、PostgreSQL、ORM、前端技术栈；
- 删除历史 migration、库存流水或核心功能；
- 改变既有库存事务语义；
- 使用 SQLite 作为正式生产数据库；
- 引入复杂微服务、Kubernetes 或不必要基础设施；
- 强制使用 Docker Desktop；
- 暴露 PostgreSQL 到 LAN/公网，或默认公网暴露 FastAPI；
- 提交密钥、本地数据库、导出、缓存、虚拟环境或构建产物；
- 以 `create_all()` 代替生产 Alembic migration；
- 让在线第三方条码服务成为核心依赖；
- 为“清理代码”破坏已有可用功能或云端备用部署能力。
